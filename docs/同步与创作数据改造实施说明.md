# 拾页同步与创作数据改造实施说明

交付对象：接手修改项目的 AI 开发者。目标：实现本机可靠保存、低干扰后台同步、自动处理数据分叉、无库存的创作规则，并安全接续已有数据与失败队列。

本说明是实施任务书，不代表功能已经实现。不得以隐藏报错、丢弃待同步记录、强制覆盖云端或关闭校验来宣称同步问题解决。验收目标是主要正常与故障场景下的数据安全、收敛和可恢复性，不是无法证明的“永远没有 bug”。

## 2 产品决策与建议默认值

### 2.1 用户已经明确的规则

1. 用户不需要手工排解同步冲突，不展示“选择本机或云端”“修订号不一致，请刷新解决”等日常操作障碍。
2. 作品有真实分叉时保留两份可编辑作品；不以操作级合并或整份时间戳胜者作为主要冲突处理方式。
3. 非作品数据发生竞争时自动采用最新修改，不创建重复素材、重复系列、重复设置或可见冲突副本。不同字段的更新可以共存；同一字段竞争自动决策。
4. 不再提供库存管理：移除数量、零库存禁用、剩余胶带长度和全局扣减。
5. 素材“已使用”只影响自动推荐搭配。正常浏览、手工选取、用户明确指定给 AI 的素材仍可使用；同一素材可用于多个作品。
6. 一个作品的创作方案中，普通素材只能取用一份；这份素材可以切成多片。不同作品与不同候选方案独立计算。
7. 胶带默认不随“作品已使用”自动变成已使用；提供设置允许用户开启联动。
8. 编辑过程本机持续可靠保存，云端主要在保存、完成、返回时提交快照；网络不能阻塞切页、删除、书写等操作。

### 3.2 用户诊断文件

来源为用户提供的 `拾页同步诊断-2026-10-15.json`，不要把原文件纳入仓库。它包含 555 个事件、17 个会话；导出时 pending=12、conflicts=2、cloudRevision=2062。

- 55 次 `conflict` 事件全是 `batch`；这是事件次数，不是 55 个独立冲突。
- 32 次 `batch/unconfirmed-response`；同一失败会在 direct、batch、queue 层重复记录，不能把所有 failed 相加当成失败请求数。
- 12 次 `queue/unknown` 的 TypeError，需要结合构建与源码映射定位，不能猜测为某个当前函数的确定 bug。
- 40 次 lock-entered 的等待为 0–4ms，不支持浏览器同步锁是主要瓶颈的结论。
- 完成的 prepare 阶段中位数约 1.164 秒，最大约 128.857 秒；后台挂起可能计入耗时。成功 committed 事件 8 次，中位数约 7.316 秒，不是生产 SLA。
- 同一天多个构建文件名说明运行过不同构建，不证明更新本身制造了冲突。基线 2048、2052 的旧批次反复出现，说明需要核查遗留队列处理。

先建立可追踪、去重的诊断，再用真实服务端请求阶段数据定位提交超时，不用统一延长超时或降低频率掩盖根因。

## 4 总体架构

保留三层分工：编辑器生成领域修改；本机事务可靠保存；同步服务在后台提交不可变快照或字段操作。页面不直接控制网络重试、修订号、冲突副本和账号锁。

```text
手工编辑 / AI 接受结果 / 导入
              ↓ 同一领域校验与语义变更判断
账号隔离本机草稿 + 图片引用 + 本机变更序号
              ↓ 保存 / 返回 / 恢复快照触发
不可变上传任务与依赖清单
              ↓ 图片与正文对象准备（数据库事务外）
服务端短事务：去重 → 单记录检查 → 自动决策 → 收据与变更游标
              ↓
本机确认指定任务；更晚草稿不被清掉；局部更新界面
```

不引入实时多人协作 CRDT/OT。Scene v2 仍是作品正文；撤销历史和编辑操作日志不再充当云端合并依据。作品名称、草稿/完成状态等业务内容要明确分类，不能把所有字段都排除指纹。

### 4.1 必须始终成立的不变量

1. 显示“已保存到本机”之前，相应正文和必要的新图片已完成 IndexedDB 事务。
2. 上传确认只能清除它对应的任务与已确认本机代次，不能清除后来编辑。
3. 同一操作 ID 的载荷不可变；相同 ID 不同载荷必须拒绝，不可重新解释为成功。
4. 一份本机独有作品只允许在服务端确认对应正文或保护副本后退出上传队列。
5. 非作品自动输掉竞争后，本机也应用权威结果；不能保留“看起来成功”的本机假象。
6. 正文引用的对象必须存在、属于当前账号；副本不得只保存列表摘要。
7. 不因账号其他记录的变化把当前记录判为业务冲突。
8. 删除具有明确身份；旧保存、超时重试不能复活删除。
9. 缓存淘汰、登出、升级不能把待同步草稿与字节当可丢弃缓存清除。
10. 普通记录竞争可有舍弃的旧值；作品竞争不得静默丢弃独立创作。

### 5.1 语义指纹

定义一个共享、纯函数的 canonical serializer，不在不同文件各自 JSON.stringify 后比较。对象键稳定排序，数组保留有意义顺序；不要为凑相等把坐标粗暴取整。区分 null、字段不存在以及必要默认值，禁止 NaN/Infinity。

作品指纹包含所有方案的图层、纸张、正文、固定素材引用、用户存档以及需同步的真实业务状态。仅用于 UI 的选中、缩放、滚动、编辑会话、上传进度、派生封面路径、诊断和自动计时时间不进入正文指纹。业务元数据可独立指纹；明确活动方案是用户作品选择还是本机查看位置，默认查看切换不制造内容修改。

自动快照和撤销尾部不得单独造成“作品内容改变”；手动创建的存档是用户明确操作，应持久化。内容 hash 与完整请求 payload hash 职责不同，不能混用。

no-op 必须覆盖各入口和持久层兜底：打开/关闭、无变化表单、重复点击完成、保存后撤销回已同步内容、封面补齐、升级、后台分类无变化。若撤销期间中间版本已上传，则需要把撤销后的内容作为新快照恢复；不能只跟最初打开基线比较而漏传。

## 6 本机草稿和上传调度

### 6.1 本机可靠性

- 本机草稿与账号隔离持久 outbox 是受保护数据，图片 LRU 是可淘汰缓存，必须清晰分离。
- 每个已提交编辑动作串行进入本机持久队列；可短时合并写入但必须有上限。完成笔迹、文本失焦、切页和显式保存要等待本机写入完成，不能仅设置定时器。
- 本机 `localGeneration` 单调递增，恢复后继续；写入失败保留内存和原持久副本，显示“尚未保存，请勿关闭”，不能继续宣称成功。
- 同账号、作品、独立编辑会话分别保留草稿，跨标签页锁加 IDB 原子事务控制；BroadcastChannel 只用于通知，不能作为正确性保障。
- `visibilitychange/pagehide` 只是尽力补救，不承诺浏览器强退后 JS 继续运行。下一次打开从已持久状态恢复。

### 6.2 上传任务状态机

建议状态：`ready → preparing → committing → acknowledged`；可进入 `retryable`、`authRequired`、`pausedForUpgrade`、`invalidData`。业务分叉由自动决策产生 `forked` 成功结果，不留一个等用户排解的 conflict 状态。

任务包含不可变快照、依赖引用、来源基线、分支和代次。尚未发送的同分支旧快照可被新快照替代；已进入不确定提交状态的任务不可换载荷，必须先查收据。之后的新编辑作为后继任务，收到前序确认后再绑定正确的云端基线。

队列必须有持久状态、nextAttemptAt、attempt、最后失败类别；页面重载不能把退避归零并重试风暴。无关作品可继续；同一作品分支与删除/恢复保持顺序。准备图片失败不能阻塞无依赖的纯元数据。

5xx/网络/超时：带随机抖动的有界退避，尊重 Retry-After；鉴权：暂停相关账号并等待重新验证；非法数据：保留原件和可导出诊断，不无限热重试；格式过旧：保留草稿并提示更新或转换。不得根据中文错误消息正则作为唯一状态判断，应使用结构化错误码。

## 7 服务端提交与增量读取

### 7.1 提交协议

在现有数据库/RPC上扩展，函数名由实施者确定。请求至少携带协议、账号 epoch、operationId、规范化 payloadHash、实体/字段操作、基线和不可变对象引用。账号从认证身份取得，不信任请求声明的 userId。

事务中顺序建议：验证身份和协议 → 检查幂等结果 → 按一致顺序锁定相关记录 → 检查 epoch 和每记录基线 → 自动业务决策 → 写记录及副本映射 → 写操作结果和增量事件 → 提交。文件哈希、压缩、COS上传和预览生成必须在事务外。

响应是结构化结果，可包括 `applied / identical / superseded / forked / deleted / obsoleteEpoch`、权威记录版本、内容 hash、目标作品 ID、操作收据、增量游标。`superseded` 是按用户规则自动选取新值的终态，不是网络失败。

账号变更游标可以通过短临界区分配，但不能继续要求所有记录提交携带全账号 expected_revision。无关记录更新不能引发反复回源、全库刷新和业务冲突。涉及多实体的删除、恢复、导入仍需真实事务边界，不把相关操作拆散。

### 7.2 幂等与收据保留

检查 `deploy/supabase/idempotent-commits.sql` 和 `storage-audit-retention.sql`。现有清理策略允许清除至少 90 天前收据，并依赖旧全局修订阻止重放。替换 CAS 后不能照搬该假设。

实现以下至少一种经过证明的策略：持久保存紧凑去重水位与副本映射；或明确操作接受窗口，过期操作转入安全核对/恢复，禁止当新操作重放。不能靠有限收据过期后“找不到就重新执行”。删除墓碑、账号 epoch、分支副本映射寿命必须覆盖被支持的离线恢复窗口。

同一操作重试返回原结果，包括原 fork 目标，不能随着云端头变化再次创建副本。重复收据本身也不可由普通客户端伪造；审计 grants/RLS，确认权威记录写入不能绕过新协议。

### 7.3 增量读取

保留账号隔离快照和按变更键拉取。游标连续可增量；日志缺口走完整核对，不把缺口直接当用户冲突。更新单个记录、封面和状态，不强制重建整页。

本机脏稿不能被拉取快照直接覆盖。拉取结果落入 remote head，由编辑会话显式决定接受、保持当前草稿或分叉。首次登录先验证身份再显示私有缓存。

## 8 作品自动分叉协议

### 8.1 决策表

| 状态 | 自动动作 |
| --- | --- |
| 本机内容未变、云端有更新 | 使用最新云端，不上传旧稿 |
| 本机与云端内容相同 | 确认 identical，不生成副本 |
| 云端仍是编辑基线 | 原作品 CAS 更新 |
| 同分支前序保存刚成功 | 推进确认基线，提交后继快照，不判为独立分叉 |
| 云端与本机分别从旧基线修改且内容不同 | 服务端保护云端原件，将本机分支提交到稳定副本目标 |
| 作品被删除，本机没有新内容 | 接受删除 |
| 作品被删除，本机仍有独有新内容 | 原件保持删除，本机内容另存恢复作品 |
| 账号 epoch 已改变 | 不自动恢复旧账号资料；保留受保护本机恢复包，执行专门恢复流程 |

以完整作品为冲突保护单位，默认包括全部方案和手动存档。仅标题/收藏等轻量元数据竞争可以采用普通字段规则，避免“改标题就复制整份”；必须明确定义作品正文与作品管理字段边界并测试。

### 8.2 稳定副本与后继编辑

服务端对 `(账号epoch, 原作品ID, 本机分支ID, 分叉锚点)` 建立唯一映射。目标 ID 由服务端分配或双方稳定推导，不能每重试一次随机生成。映射与新作品正文、引用、收据在同一事务确认。

客户端收到 forked 后，原子更新本机分支目标、当前 activeProject、待上传后继任务及本机草稿引用；不能把同一个浏览器内另一独立分支也强行重定向。已经发出的不确定请求仍按原 operationId 核对，不能篡改其载荷。

新副本有独立 project ID，层 ID 可以保留在作品内部。审计所有以 project ID 为键的缓存、手动存档、AI 任务目标、封面、草稿、使用状态操作和路由。后续保存只更新该副本，不再每次从原作品创建新副本。关闭重开、重启浏览器和重试都必须维持映射。

副本不得自动触发“已使用素材”联动；原图引用共享不可变字节，不重复上传所有素材。普通字段、图片修改不产生新的可见素材副本。

## 9 非作品最新修改规则

### 9.1 精确修改而非旧整条覆盖

普通记录使用字段或原子字段组操作。名称、备注、收藏、使用状态独立；图片引用与其尺寸/蒙版元数据作为一个原子组，不能分别选新值造成不匹配；标签默认作为一个完整字段采用最新修改，符合用户接受低成本覆盖的要求，不额外引入标签 CRDT。系列成员归属存于权威归属字段，避免系列列表和素材记录双写分叉。

只把真实变化的字段排入队列。收到权威结果后更新本机；不新增“冲突副本”或让任务永久 pending。

### 9.2 最新的可实现定义

不得把重试时间当编辑时间，也不得声称离线且设备时钟错误时能绝对还原现实先后。

建议记录字段的因果版本及持久逻辑时间：有因果先后时以后继为准；独立离线修改用固定排序的 editStamp（经在线校时的时间分量、逻辑计数、稳定客户端ID/操作ID）决胜。时间戳在实际编辑时生成，重试不变；设备时间倒退、跳到未来、校时前离线都必须有规则，不允许一个错误未来时间永久压制正常修改。服务端拒绝/规范化异常时间时要固定结果并记录诊断，不能每次重试重新排序。

实施者可选更简单的确定性排序，但必须在协议说明中明确离线竞争的取舍并测试；不能悄悄退回“谁最后重试谁获胜”。这属于非作品的低风险自动决策，不需要用户手工选版本。

### 9.3 删除优先于迟到的普通保存

“最新值”只适用于正常字段竞争。删除创建带 epoch/实体代次的墓碑。基于删除前版本的编辑被自动舍弃；明确 restore 操作才能恢复。系列被删除后，迟到的素材归属变更应自动归入未分类或按既定规则清理，不重新创建系列。

跨实体依赖必须处理：删除素材时仍被作品引用的图片与来源版本保留；删除作品不删除其他作品共用图；最近删除 30 天与服务端延迟回收继续遵守仓库规则。清空账号不能解释为普通字段覆盖。

## 10 打开作品与后台刷新

1. 显示已验证账号的缓存卡片/预览，不把全账号队列清空作为打开前置条件。
2. 为这次打开生成 request/session token，查询该作品最新 head（版本、hash、删除状态和必要引用）。
3. 没有本机新内容时，head 不变复用缓存；变化时按新不可变文档路径取正文，完整校验后进入可编辑状态。
4. 存在本机新内容时，先持久保护，自动核对/提交或建立分叉；网络慢时允许进入明确标注的离线草稿，不丢弃它去展示旧云端。
5. 网络失败或超时有上限，不能无限显示“正在打开”；缓存预览可立即显示，未经核对不标“最新云端”。无缓存则显示不可用与重试。
6. A作品打开过程中点击B，A的迟到响应不能改变当前画布；切账号、删除目标、退出编辑同样处理。
7. 打开时核对不能代替保存时 CAS。用户正在输入或画画时后台远端变化不得替换画布；新 head 留作后台状态，保存时自动保护分叉。

AI 生成也绑定账号、project、draft、branch和启动基线，不能将迟到结果写入后来打开的作品。沿用手改保护与候选方案机制；AI 候选方案和同步分叉作品是两种不同业务，不能相互重复复制。

## 11 去库存与单方案素材约束

### 11.1 删除的行为

移除 supply.quantity、999 哨兵、库存为零禁用、胶带 availableLengthMM 限制，以及相关表单、筛选、推荐、AI prompt/schema、离线任务包说明、错误文案、导入导出校验和测试假设。不要只隐藏表单而让深层校验仍拒绝。

### 11.2 保留的能力

- 物理尺寸与纸张比例、素材来源、裁片 source geometry、余料/废料几何和显示片段身份。
- 普通素材在一个方案中只拥有一个源实例；多个裁片来源不重叠，裁切不超界。隐藏/停放不释放已经取用的来源；显示投影片段不算新素材。
- 胶带建议允许多个独立段实例；同一段的裁片仍不能重复占用来源。无缝重复仅针对显式验证为可重复图案的胶带，不拉伸图像伪造实际尺寸。
- 所有手工、AI、Scene导入、任务包返回、复制、恢复、新增图层共用一个领域校验入口，返回结构化诊断。不要继续让 `domain.validatePhysicalDraft`、`creative.checkDraft` 和 ledger 各自定义相反规则。

“一个方案一次”按 asset ID 的源实例身份判断，不做视觉相似去重；用户导入了两条不同素材记录不自动合并。复制普通完整素材应提示已在方案中并定位，而非生成第二份；允许复制文字、图形、独立方案与作品。

### 11.3 现有作品迁移

不得因取消库存，删除已保存作品中第二张贴纸、合并裁片或重编号导致几何错乱。转换工具应把明确可映射的 materialUnitIndex 等转换为当前显式来源实例；发现旧作品合法使用多份普通素材时，完整保留为受保护的既有布局，禁止继续新增重复取用，或者在独立转换工具中报告需产品处理的记录。不得悄悄把它们裁掉以通过校验。

尽量保持现有 Scene v2 可读取，新增规则用于创作变更；确需变更文档格式时按第15节执行。渲染器应能显示受保护的历史布局，不能先禁止打开再要求用户修复。

### 11.4 已使用和推荐

新增偏好建议 `markTapeUsedWithProject=false`，加入非敏感云偏好白名单和设置界面。中文名称：“标记作品已使用时，同时标记胶带为已使用”。

用户显式将作品标为已使用时，冻结当前方案实际使用的素材 ID 和当时偏好值，生成幂等业务操作。作品状态与素材使用标记应在同一可靠事务/可证明的业务流程中完成。重试不得重新遍历后来变化的方案，也不得把整个素材对象写回覆盖其名称、标签。

当前代码遍历所有 drafts，必须改为明确的当前方案。取消作品已使用、删除作品、恢复作品、生成同步副本都不反向改变素材状态。对已使用作品继续编辑不自动标记后来加入的素材；用户再次明确执行“标记本方案素材已使用”才处理。

推荐排除 used；用户手选、加入本次核心素材、指定 AI 输入不排除。删除/隐藏、无法读取图像等可用性限制仍有效，不能把“已使用可选”误写为“任何损坏素材都可选”。

## 12 图片和作品引用稳定性

作品应固定引用不可变图片内容版本及必要来源尺寸。素材库抠图、改尺寸、换图采用最新结果，但不得追溯改变旧作品外观。这是内部资源版本，不是用户可见素材副本。

新导入/加工先可靠保存 Blob，上传内容哈希对象，确认后提交引用。对象成功但元数据失败形成暂时孤立对象，由受保护回收流程处理；不要在浏览器失败回调立即物理删除。

封面与正文独立：正文成功可显示“已同步”；封面单独后台任务按 sceneHash 更新，失败重试不回滚正文、不增加正文版本；迟到旧封面不能覆盖新内容封面。封面字段更新必须仍能触发其他设备对应缓存失效。

保持固定480px卡片、按需档位、账号隔离缓存、内容哈希复用和受限并发。导出才读原图。显示缓存失效贯通 AbortSignal，取消共享资源时使用引用计数，不能取消另一个仍需要它的读者。服务端自托管应有缩略图读取，不继续把原图伪装成预览。

最近删除、历史存档、冲突副本、本机待同步引用都属于保护集合。服务端不能声称知道从未联网上报的离线依赖；必须结合设备保护水位/保留期及本机字节保障设计延迟 GC。无法证明安全则推迟回收，不牺牲作品恢复。

## 13 后端与客户端边界

`store.js/storage-router.js` 保留明确模式，不因网络错误切换另一资料库。

- 云端：账号隔离本机草稿/outbox + 私有对象存储 + 单记录提交协议。
- 浏览器：同样的创作校验和本机可靠事务，没有“云端已同步”假状态；同浏览器多标签页仍需保护独立分支。
- 自托管：若继续作为受支持数据模式，应补上对应持久 outbox、幂等提交、实体版本、删除规则和预览接口。只修改云端而宣称所有模式成熟不合格。

离线浏览器存储仍受系统空间、站点数据清除、设备损坏影响；请求持久存储权限可改善但不构成绝对保证。不得把未上传数据与可自动淘汰的图片缓存共用同一清理规则。

## 14 状态与诊断

正常用户仅需看到：保存中、已保存到本机、等待联网、正在同步、已同步、已保留另一编辑版本。鉴权/本机存储失败/格式不支持可以显示有意义的处理提示，不能假装这些也是自动成功。

删除日常人工冲突弹窗和“放弃全部待同步”作为常规修复入口；保留诊断导出、保护性备份和受控恢复工具。不要把冲突弹窗删掉却把失败队列永久隐藏。

诊断增加 build、syncProtocol、稳定匿名任务关联ID、阶段、依赖数量/字节、前后台状态、重试次数、CAS结果、fork目标关联标记、无变化跳过、服务端requestId及收据结果。不要记录正文、签名URL、密钥和原始私人图片。

耗时分离：本机持久化、排队、图片准备、网络请求、数据库事务、确认处理、前后台挂起。使用单调计时并识别后台冻结，避免把17分钟挂起标成17分钟CPU卡顿。同一请求多层失败日志可关联去重。

## 15 迁移与当前失败队列修复

### 15.1 迁移顺序

1. 固定执行基线，记录修改前测试结果；用合成资料建立完整备份、恢复、失败队列恢复测试。
2. 盘点现有运行时合同、服务端实际 schema/RPC、RLS和保留策略；仓库SQL不等于生产已经部署。
3. 加法部署新服务端结构、协议和读接口，在隔离环境验证；不要先删除旧字段/表。
4. 为旧客户端写入设置明确闸门，旧客户端保留本机草稿并提示更新，不再经旧RPC绕过新规则。无需长期维护两套日常写入逻辑。
5. 当前格式作品直接继续使用；需要格式变更的用独立转换工具先扫描、备份、确定性转换、校验。无法识别的原样保护，不进入无限重试。
6. 失败队列经下面的安全重建流程转换；新队列与原始恢复副本可靠持久化后原子切换。
7. 验证新客户端在更新、重载、PWA旧标签页、断网恢复时都能收敛；再移除无用旧日常入口。
8. 更新文档和生成运行时，测试站验收，再按仓库发布流程处理正式发布。

### 15.2 安全重建不能伪造基线

输入包含本机完整作品、队列原图、操作身份、删除/恢复意图和可获得的云端权威记录。先检查原 operationId 收据，再比较实际内容。

- 已完成：清理对应任务，不重新执行。
- 内容相同：确认完成，不增加版本。
- 本机独有作品变化：在能证明基线未变时提交；不能证明时自动保留独立作品，不能强行覆盖。
- 非作品：转换为有固定编辑stamp的字段/原子组操作，按正常最新规则处理。
- 删除/恢复：保留原身份和实体代次；账号曾重置时不得把旧数据自动灌回。
- 缺字节或未知格式：隔离保护并给诊断；不丢弃也不无限热重试。

新旧队列替换在一个本机事务中进行；中断可恢复。不要先 discard 再从界面列表重建，因为列表可能只有摘要，并且遗漏导入图片、最近删除和其他会话草稿。

### 15.3 回滚

服务端加法迁移与功能开关支持暂停新上传。回滚不能让旧客户端写坏新文档；必要时只读而保留本机编辑。对已创建的副本映射、收据和墓碑不做破坏性回滚。真实账号迁移前备份并做隔离恢复；生产数据动作按当前用户授权范围执行，不擅自清空。

## 18 性能与完成标准

设定并公布可复现环境、数据量、网络条件后测量，不能把网络不可用算成任意保证的SLA。

- 无变化保存新增正文上传和数据库内容修订应为0。
- 同一分支未发送的多次变更应合并，不能随每笔书写产生独立云端作品提交。
- 本机保存延迟、当前作品打开核对、纯元数据提交、带新图片提交分别报告P50/P95与字节数。
- 纯元数据不得等待无关大图片准备；保存/返回不得等待网络；准备图片不得持有数据库事务锁。
- 低清卡片不回源原图，内容未变不重复上传相同图片；旧请求可取消但不能误伤共享读者。
- 正常竞争任务最终进入已处理状态，不出现需要用户选择才能清空的冲突任务。
- 有故障时状态真实、数据可恢复，有明确重试/重新登录/更新路径；不能声称所有错误都能自动恢复。

最终交付必须包括：代码与迁移、协议说明、数据转换/回滚方案、测试结果、真实设备验收记录或尚未完成的真实限制、性能对比、已知问题、更新的架构文档和无隐私泄漏的变更清单。不得仅以“测试通过”省略没有执行的数据库/真机验证。
